# Roomba+ 4.4.0

**The cleaning path lies on the floor plan; room tracking follows the
robot's position where it has one, and a new start during a mission
replaces its room plan; the live path of a
robot whose map was turned in the iRobot app
follows the map the robot saved itself, with a setting for where that
reads wrong; a robot that freed itself is no longer filed as having
given up; the robot's address stays out of the diagnostics; eleven
error codes nobody can source are gone; and the credits say where
things came from.**

## The live path and a map turned in the app (@frnchfrgg)

4.3.4 turned the positions a robot answers back by the turn saved in
the iRobot app, read from the map's header. @frnchfrgg's i7+ needed
that on 9 October. On 11 October, with the same angles in the header,
his path came out a quarter off the other way: the robot had answered
unturned.

What differed was the map versions. On 9 October the version the robot
saved itself (`robot_pmapv_id`) was newer than his edit in the app. On
11 October it was older: it came from a mission after he had set the
map back, and he turned it again afterwards. Both fit a robot that
answers in the map it saved itself, and picks up a turn from the app
only once it has saved a map after a cleaning run.

- **The turn is now read from the robot's own map version.** Roomba+
  fetches that version's map once and takes its angles. Where the
  robot's version is the committed one, nothing extra is fetched; where
  the fetch fails, the committed version's angles count, as before.
- **Turn of the live path** (Configure → Connection settings, beside
  *Ask the robot for its position*): *Automatic* by default, or 0°,
  90°, 180° or 270° for a robot where Automatic reads wrong. If you set
  an angle, please attach the diagnostics to an issue, so that
  Automatic can learn your robot. Suggested by @frnchfrgg.
- **The diagnostics** say which version the angle came from
  (`requested_path_turn_source`: `robot_version`, `map_version` or
  `setting`), which angle is drawn (`requested_path_turn_drawn_deg`),
  and the robot version's own angles (`cloud.umf_poses.robot_version`).

Two downloads fit this, which is not yet proof. If it is right, the
path lies on the rooms map both before and after the robot has picked
up a turn from the app.

## The cleaning path on the floor plan (@frnchfrgg)

The cleaning path was drawn on its own: it showed where the robot went,
not where that is in the home. Its picture fitted the floor covered so
far, and grew with it.

- **The rooms of the cloud map are drawn under the path**, filled and
  outlined, with their names when *Draw room names on the map image*
  is on. The picture fits the whole floor plan from the start of the
  run, so it no longer zooms while the path grows.
- **For a robot that is asked for its position** (an i-series on lewis,
  for example) the rooms go in in the cloud map's frame, the frame the
  positions are drawn in, without waiting for alignment. A path that
  runs through walls says the turn of those positions is wrong; *Turn of
  the live path* fixes it.
- **For a Smart Map robot that reports its own position**, the rooms go
  through the alignment, once there is one, as the keep-out zones over
  the path already do.
- **A 900-series** keeps the outlines of its areas, as before.

## The room from the robot's position (@frnchfrgg)

Room tracking moved through the planned rooms on phase changes and
drives, and judged a room done from the time spent in it against an
estimate. @frnchfrgg's i7+ cleaned in another order than Roomba+
expected, and the room start and end events matched nothing that
happened.

**His run also had a plan that was wrong.** Roomba+ sent a start for
two rooms, then one for six, nine seconds into the mission. The plan was
built once, at the mission's first `run`, so room tracking expected two
rooms for a six-room run.

- **A new start during a mission replaces its room plan.** The run time
  stays; the rooms start over with the new plan. Only a `start` does
  this, not `find`, `dock` or `stop`, and not the first message after a
  restart of Home Assistant, which keeps the stored progress.
- **A robot whose position is known is placed in a room.** That works
  for positions the robot answers when asked (his i7+), on a Smart Map
  whose rooms are in the cloud, and for a robot's own position: on a
  Smart Map once Roomba+ has aligned it, on a 900-series in the areas
  Roomba+ divided its floor into.
- **A room counts after 15 seconds in it, while cleaning.** Crossing a
  doorway or a hall changes nothing; positions outside every room
  change nothing; the drive home does not count.
- **The display follows the robot's order.** `room_completed` fires for
  the room it left, with the time it spent there. The countdown covers
  the rest of the room and the rooms not yet entered. A room outside a
  planned run's rooms is passed through.
- **A whole-home run lists its rooms as the robot enters them**, on
  Smart Maps and 900-series alike, with a `room_completed` for each.
- **Without positions, nothing changes.** While positions place the
  robot in rooms, phase changes and estimates do not move the room.
  When they stop for a minute, those take over again.
- **The room sensor says where its room came from:**
  `current_room_source: position`.
- **The diagnostics** show the rooms seen by position
  (`rooms.tracking.visited_rooms`, `rooms_from_positions`) and the
  tracker (`position_room`: current room, last position's room, seconds
  since the last position).

A requested position is placed in a room in the cloud map's frame,
after the turn described in the next section. Where that turn reads
wrong, the rooms read wrong too, and *Turn of the live path* fixes both.
Placing positions in rooms has not been checked against real room
boundaries yet.

**A mission whose end was missed** no longer hands its room index to the
next one; it did before, and now would have handed on its rooms seen by
position too.

## A stuck the robot got out of (@Hardy-196)

@Hardy-196's i7+ reached its zone, cleaned it and drove home, and the
mission was recorded `stuck_and_abandoned`. The robot's stuck counter
had gone up once on the way.

Whether a robot carried on after a stuck is decided from the cloud's
record of the mission: a pass finished after the stuck, or a drive to
the dock after it. At mission end that record is almost never there
yet, so a clock decided instead: less than five minutes between the
stuck and the end read as abandoned. Nothing looked again once the
record arrived.

- **The record keeps the time of the stuck** (`stuck_at_ts`).
- **When the cloud's record arrives**, a mission recorded as abandoned
  whose timeline shows a finished pass or a drive home after that time
  becomes `stuck_and_resumed`, once.
- Missions recorded before 4.4.0 have no stuck time and stay as they
  are.

## The robot's address stays out of the diagnostics

The config entry's `host` went into the download as entered. Roomba+'s
diagnostics carry no address; it is redacted now.

## Error codes without a source removed

Codes 130–134, 140/141 and 160–163 came into the error table with 2.5.0,
credited to "ia74/jeremywillans references". Neither of those projects
has them. Neither do roombapy, dorita980, rest980, the Classic iRobot
app (7.18.0) or the Prime app (3.2.0). Their texts ("Mission failed",
"Hardware error", …) were written here, without a source to write them
from.

A robot reporting one of these codes now shows the code itself, like
any other code Roomba+ has no text for: the last error sensor keeps the
number, its description and action stay empty, and the repeated-error repair calls it
"Error 131". That is less than before, but it no longer tells you
something nobody knows.

If your robot does report one of them, the code and what the robot was
doing at the time are welcome in an issue.

## Under the hood

- `cloud_coordinator.umf_position_turn()` returns the turn and its
  source; `requested_position_turn()` applies the setting
  (`live_path_turn`, `const.LIVE_PATH_TURN_CHOICES`). The coordinator
  keeps the robot version's angles per map and version
  (`_robot_version_orientation()`); a failed fetch is not retried for
  that version.
- `DIAG_REDACT_KEYS` gains `host`.
- `MapRenderer.set_floor_plan()` / `floor_plan`: layer 1.4, drawn first
  and part of the fit; `RoombaMapImage._floor_plan()` places the rooms.
- New `position_room.py`: `PositionRoomTracker` (15 s and 3 positions
  per room, active while a position lay in a room within a minute) and
  `room_at_position()`. `MissionTimerStore.enter_room()`, `visited_rooms`
  and `rooms_from_positions` (stored); `set_mission_plan(replan=True)`;
  `callbacks._apply_position_room()`. The tests for it are in
  `test_image.py`, which feeds it; the suite is at its file limit.
- `const.recovered_after_stuck()` is the one rule for a stuck the robot
  got out of, used at mission end and by `MissionStore._merge_cloud_fields()`
  (correction B1-RES). Mission records gain `stuck_at_ts`.
- `const.ERROR_CATALOGUE` and `error_translations` lose the eleven
  entries; `get_localized_error_entry()` returns `{}` for them, so
  callers fall back to the raw code as they do for any unknown code.
- Comments that gave the number of codes in the table (125, 75) are
  gone; both were already wrong.
