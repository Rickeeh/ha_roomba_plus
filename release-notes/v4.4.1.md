# Roomba+ 4.4.1

**Turn of the live path turns the path already drawn, so an angle can
be checked against the floor plan; Map rotation, size and scale apply
to every picture as soon as they are saved; the cleaned area is seen
through, with the room names on top; a skip moves room tracking on and
sends the robot home properly from the last room; and a battery reset
starts capacity retention afresh.**

## Turn of the live path, on the path you see (@frnchfrgg)

@frnchfrgg set *Turn of the live path* to 270°, reloaded, then to 0°,
reloaded again, and the path stayed exactly as it was, a quarter off
the floor plan. The setting did nothing he could see.

It did reach the next mission only. A position the robot answers is
turned when it arrives and kept turned, in the picture and in storage,
so a path already drawn kept the turn it was drawn with. His path came
from a run under 4.3.5, which turned it a quarter the wrong way; 4.4.0
drew it on the floor plan, and the mistake became visible.

- **The path drawn so far turns with the setting**, as soon as the
  options are saved, about the dock: during a run and after it.
  Switching back to *Automatic* returns to what Automatic read for that
  run, not to a turn saved in the app since.
- **The turn is kept with the saved path**, so a reload or a restart
  after changing the setting turns it as well.
- A path saved before 4.4.1 has no turn kept with it and stays as
  drawn, until the next run replaces it.
- The diagnostics add `requested_path_turn_in_picture_deg`: the turn
  of the path in the picture. `requested_path_turn_drawn_deg` remains
  the turn a run starting now would get.

## Map rotation, size and scale, at once

*Map rotation*, *Map canvas size* and *Millimetres per pixel* were read
once, when the integration set up the cleaning map and the coverage
grid. The rooms map reads the rotation for every picture. Saved, the
rooms map turned and the path did not until the integration was
reloaded (@frnchfrgg: "some of these settings do not apply to some of
the maps").

- **The cleaning map and the coverage map follow as soon as the options
  are saved**, during a run too, without a reload: a reload would cost
  a running mission its path.
- **A saved path is converted to the canvas it is restored on**, as it
  already was to a new rotation. A path saved before 4.4.1 does not say
  which canvas it was drawn on and is taken as drawn on the current one,
  as before.

## The cleaned area, seen through (@frnchfrgg)

The wide light-blue band of cleaned area covered the floor plan and its
names. It is now laid over at half opacity, in a colour that looks the
same as before over white, so the rooms and their outlines show
through. The path stays opaque. The room names are drawn last, over the
path.

## Skip, as the robot takes it (@Thonno)

@Thonno's i7+ took the skip of its first room and drove on to the
second, which confirms on a second robot that skip arrives as the app
sends it. Roomba+ made two mistakes around it:

- **Room tracking stayed on the skipped room** for the rest of the run.
  A skip moved nothing, and no position found a room to move it.
  Now a skip works in two steps:
  - **At once**, the skipped room counts as done: the end of the mission
    no longer waits for it, and the remaining time leaves it out.
  - **Where the robot is** needs evidence. A position confirming a room
    moves the display, as before. Where none has after 20 seconds, the
    time the iRobot app shows "skipping", the display moves to the next
    planned room, unless the latest position still lies in the skipped
    room: then the robot did not take the skip and the display stays.
- **Skipping the last room sent a bare `dock`**, and an i7+ does not take
  that while it cleans: 20 seconds and a minute later it was still
  cleaning the room. It now goes home as *Return to base* does, paused
  first, then docked. Because the `dock` had become the robot's last
  command, every later skip in that run was refused with "Only a room
  mission started with its map can skip a room"; with the robot going
  home, that no longer arises.

The diagnostics count, for each mission, how many requested positions
fell in each room and how many in none (`position_room.positions_by_room`).
His positions found one room on the way out and none after it, which a
turn of the path, or the rooms, would explain; the counts show which
without a coordinate in the download.

## A new battery, a new baseline (@azrael)

After a new pack in his i7 and the *Battery replaced* button,
`battery_capacity_retention` read 573.4 %, and stayed there. @azrael
traced it in the source: the sensor divides the current `estCap` by a
baseline taken once, at the first reading ever, and nothing reset it.
His old pack's baseline was 436 mAh; the new one reports about 2500.

- **The battery reset clears the baseline**, by button and by the
  `roomba_plus.reset_battery` action alike; the next reading takes a new
  one from the new pack.
- **The baseline is taken from a charged pack only**, at 95 % or more.
  His 436 mAh came from a reading at a low charge; until a charged
  reading arrives the OEM capacity stands in, as before the first one.
- **The old pack's estCap readings are forgotten too.** The end-of-life
  estimate learns how much estCap jitters between readings; the jump
  from one pack to the next would have counted as one such reading and
  kept any real decline below the noise.

## Under the hood

- `MapRenderer.transform_path(fn, dtheta_deg)` moves every drawn point
  by a linear map of the frame `add_pose()` takes; `requested_turn_rad`
  holds the turn of a requested path for the diagnostics and is cleared
  by `reset()`. `dump_state()` adds `size_px` and `scale`, and
  `restore_state()` converts between canvases.
- `RoombaMapImage._sync_live_turn()` turns the path by the difference
  between its turn and the setting, out of the renderer's mirror and
  back. `_target_live_turn()` keeps what Automatic read per run
  (`_live_turn_auto_rad`). The saved map state adds `live_turn_rad` and
  `live_turn_auto_rad`.
- New dispatcher signal `const.map_options_changed_signal()`, sent when
  options are saved without a reload; the cleaning map listens
  (`_handle_map_options_changed()`), moves its renderer
  (`MapRenderer.reconfigure()`) and sets the grid's turn, and the
  coverage map is told to draw anew.
- Turning or moving a path recomputes its pixels from the millimetres
  where it has them (a path drawn in this session), so they come out
  as `add_pose()` would place them; a restored path is converted from
  its pixels, to within a pixel.
- The mission checkpoint carries the turn too, so a mission resumed
  after a restart goes on with its own turn, not with that of the last
  finished path restored at startup. Found in an independent review of
  this release, as were the exact pixels and the reload that would have
  cost a running mission its path.
- `CLEANED_ALPHA` and `CLEANED_LAYER_COLOUR`; `_draw_floor_plan_names()`
  is split from `_draw_floor_plan()`.
- `MissionTimerStore.mark_skipped()`, `next_unvisited_after()` and
  `move_to_room()`; `IRobotVacuum._track_skip()` with `SKIP_SETTLE_SEC`
  (20). The last room's skip calls `async_return_to_base()`; the skip
  record says `paused_first`.
- `PositionRoomTracker.counts` and `still_in()`; `diagnostics()` adds
  `positions_by_room`.
- `MaintenanceStore.reset_battery()` clears `baseline_estcap`;
  `RobotProfileStore.forget_battery_readings()`;
  `services.async_forget_old_battery()`, called by the button and the
  action; `sensor_helpers.BASELINE_MIN_BATTERY_PCT` (95).
