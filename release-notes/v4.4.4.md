## Skip current room (#178)

Since 4.3.7, `vacuum.send_command` with `command: skip` sends what the
iRobot app sends. It is confirmed on two Classic robots: @Thonno's i7+
left the room and drove on to the next one. 4.3.4 promised a button once
skip was confirmed, and here it is.

- **`button.<robot>_skip_current_room`**, on Classic robots that offer
  skipping (`cap.mc` 2 or 3, as the app checks).
- **It can be pressed only while the robot cleans** (phase `run`). The
  app greys its skip out otherwise.
- **Pressing it is the command itself.** The same code builds the app's
  payload, refuses with the reason where the app would not offer skip,
  sends the robot home from the last room, moves room tracking on and
  keeps the attempt in the diagnostics (`field_evidence.skip_attempts`).
- **No button on Prime robots.** The command sends them the plain `skip`
  their app sends, but no Prime robot has been seen taking it.

Skip was described only in the release notes until now. It has its own
section in [FEATURES.md](../docs/FEATURES.md#skipping-the-current-room-command-437-button-444):
the command with `params: {room: …}`, the conditions with the refusal
each one gives, the last room, and what room tracking does after a skip.

## Combo j7+ and j9+: local, not cloud-only

@kyoheimukaida's Combo j9+ (`c975860`), added from the iRobot account,
was set up **cloud-only**, on the Prime backend. It is a Classic robot
and works on the local connection, rooms and mopping included; the
reporter proved that with a patched copy. Two things were wrong:

- **Its SKU was unknown.** The Combo j-series starts with `c`, not `j`,
  and the Classic table had neither `C7` nor `C9`. Roomba+ sends an
  unknown SKU down the Prime path, because new models are Prime.
  roombapy-prime 0.7.1 adds both, from real robots (`c755020`,
  `c975860`). A Combo j7+ or j9+ added from the account now takes the
  local path, and both appear in the local robot list, where they were
  missing.
- **Reconfigure kept `cloud_only`.** It checked the new local address
  and password, then saved them and left the entry on the cloud path.
  A cloud-only entry whose local connection works is now switched to
  the local connection. The entry stays, with its account and options.
  A Prime robot has no local connection, so it never gets this far.

**Reconfigure takes the robot password from the account.** The
password field may now be left empty on a robot set up with an iRobot
account: Roomba+ takes the password from the account's login, as it
does when it adds a Classic robot from the account. So a robot that ran
cloud-only needs only its IP address. Without an account, or when the
login has no password for the robot, the form says so and asks for it.

**Already set up as cloud-only?** Open the robot's entry, choose
*Reconfigure*, enter the robot's IP address and leave the password
empty. The entities the cloud-only setup created stay behind as
unavailable; remove them from the device page.

## An account without robots says why (#218)

Adding a robot through the iRobot account ended with *"No new robots
found on this iRobot account — every robot is already configured"*
whenever the account returned no robots. For @jstride, who had nothing
set up, that was simply wrong. The message now depends on what the
cloud says:

- **The robot is registered to another iRobot account.** The login
  answer can say so (`conflicted_robots`, `conflicted_user_count`; the
  iRobot Classic app reads both). The known case is a second-hand robot
  still on its previous owner's account (roombapy-prime #93). The text
  says to remove it there and add it to your own account.
- **The cloud lists robots the login did not return.** The setup then
  reads the account's device list, the one the iRobot Prime app shows
  (`/v1/user/associations/robots`). This has not been seen on a real
  account; the text asks for an issue with a debug log.
- **The account has no robots.** The text asks to check that it is the
  account the robot was added to in the iRobot app.

*Every robot is already configured* is now said only when that is true.

The fields have not been seen on a real answer yet. The debug log names
the counts (conflicting robots, other accounts, robots on the device
list) and never a robot id. The diagnostics download gains
`ownership_conflicts_on_account`, a count.

## "end-phase burst rejected" is a debug line (#207)

`MissionStore: end-phase burst rejected (time gate …) — mission still
active` came at INFO level, three times at the end of @pk-1966's
mission, and read as a fault. It is the design: the end signals have to
hold for two seconds before a mission counts as finished, and a burst
shorter than that is held back. It now logs at debug level.

## Under the hood

- `button.SkipRoomButton` calls `vacuum.send_command` on the robot's
  vacuum entity, found by its unique id; `button.robot_offers_skip()`.
- Text `entity.button.skip_room` in `strings.json` and all eight
  translations; icon `mdi:skip-next`.
- `callbacks.py`: the end-phase refusal logs with `_LOGGER.debug`.
- `config_flow._async_why_no_robots()` picks the abort reason; texts
  `config.abort.no_robots_on_account`, `robots_owned_by_other_account`
  and `robots_not_in_login` in `strings.json` and all eight
  translations. `cloud_account._conflict_count()` for the diagnostics.
- `async_step_reconfigure()`: a cloud-only entry becomes `local_push`
  once the local check passes; an empty password comes from
  `_async_robot_password_from_account()` (the held login when it lists
  the robot, a new one otherwise). Form errors `robot_password_needed`
  and `robot_password_not_in_account`; the password field's help text
  says it may be left empty. All nine text files.
- roombapy-prime 0.7.1 (was 0.6.0): the login's ownership fields, the
  device-list read and the Combo prefixes. 0.7.0 in between added a
  command-line tool only. The CI workflows install the same version.
- A change made after 4.4.3 that gave each Prime robot its own login
  was reverted before release. Two Prime robots on one account shared
  one MQTT client id and evicted each other (@mattdrmc). The fix comes
  as one connection per account in roombapy-prime, keeping the single
  login; roombapy-prime 0.7.0 brings a tool that checks it on a real
  account first.

## Tested

- The full suite passes on Home Assistant 2025 and 2026; ruff, the
  typing baseline and the per-module coverage floors pass.
- The new tests fail against 4.4.3 or when the code is broken:
  - a robot with `cap.mc` 1 or without it gets a button;
  - the button can be pressed while the robot is docked or paused;
  - the press sends another command;
  - the end-phase refusal logs at INFO;
  - a login with no robots ends with "every robot is already
    configured", or the conflict and the device list are not told
    apart;
  - the diagnostics download has no conflict count;
  - a Combo j7+ or j9+ takes the Prime path, or is missing from the
    local list;
  - Reconfigure keeps `cloud_only` after a working local check, or an
    empty password is not taken from the account (held login first,
    one new login otherwise, its error shown when it fails, the robot
    password never in the log).
